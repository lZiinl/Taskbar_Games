# 지인용 온라인 기록 경쟁 · 구현과 운영 안내

이 문서는 0.3.0에서 실제로 구현한 기능, 로컬 검증 방법, 배포 후 관리 방법을 설명합니다.
서버 프로그램과 앱 연결은 구현되어 있지만 외부 호스팅·도메인·실제 배포 URL은 아직 지정하지 않았습니다.
따라서 지금 바로 다른 집의 지인이 접속할 수 있는 공개 서버가 생성된 상태는 아닙니다.

## 1. 전체 구조

```text
Windows 앱
  ├─ 오프라인 게임 / 로컬 기록
  └─ 온라인 창
       ├─ 서버 정책 조회: 앱 버전, 경기 규칙, 현재 시즌, 배포 URL
       ├─ 초대 코드로 최초 참가 → 개인 로그인 토큰
       ├─ 경기 번호를 받아 온라인 도전 시작
       ├─ 완료한 결과 등록 / 실패 시 같은 번호로 재등록
       └─ 상위 10명 / 내 순위 조회
                 ↓ HTTPS
친구 그룹 전용 서버
  ├─ policy.json: 운영자가 관리하는 버전·시즌 정책
  └─ SQLite: 계정, 경기 번호, 시즌별 최고 기록
```

한 서버가 하나의 친구 그룹입니다. 방 생성·복수 그룹 관리·실시간 대전은 포함하지 않습니다.
앱은 원래의 .NET Framework/WinForms 구조를 유지합니다.
서버는 Python 3.10 이상과 표준 라이브러리만 사용하며 별도 패키지 설치가 필요하지 않습니다.
인터넷 운영에는 서버 프로세스를 계속 실행할 호스트와 HTTPS 연결이 필요합니다.
PC를 서버로 쓰면 그 PC가 켜져 있어야 하고, 클라우드를 쓰면 개인 PC를 켜 둘 필요가 없습니다.

## 2. 앱에서 사용하는 방법

게임 선택창을 우클릭하면 **온라인 / v0.3.0** 메뉴가 나옵니다.
기존 58×74 게임 선택창은 그대로 유지하고 설정과 순위는 별도 창에 모았습니다.

| 버튼/항목 | 동작 |
|---|---|
| 서버 | 운영자가 전달한 `https://...` 주소. 경로 없이 호스트와 포트만 입력 |
| 연결 / 확인 | 버전·규칙·다운로드 주소 조회, 서버 주소 저장 |
| 닉네임 | 최초 참가 시 2~16자. 서버 안에서 중복 불가 |
| 초대/복구 | 최초 참가용 초대 코드 또는 계정 복구 토큰 |
| 참가 | 초대 코드 확인 후 개인 계정 생성 |
| 계정 복구 | 운영자가 재발급한 로그인 토큰으로 기존 계정 연결 |
| 순위 | 선택한 게임의 현재 시즌 상위 10명과 내 순위 |
| 온라인 도전 | 서버에서 경기 번호를 받은 다음 해당 게임 시작 |
| 재등록 | 완료했으나 통신 오류로 미등록된 경기를 같은 번호로 재전송 |
| 업데이트 | 지정된 HTTPS 배포 페이지를 브라우저에서 열기 |

순위의 닉네임은 서버에서 결정합니다. 닉네임 칸을 나중에 바꿔도 기존 계정 이름이 변경되지는 않습니다.
서버에 가입한 뒤에는 초대 코드를 다시 입력할 필요가 없습니다.

## 3. 같은 앱 버전이어야 하는가?

완전히 같은 실행 파일일 필요는 없습니다. 다음 세 가지를 나누어 확인합니다.

| 구분 | 현재 값 | 바꾸는 시점 |
|---|---|---|
| 앱 버전 | `0.3.0` | 기능·디자인·버그 수정 배포 |
| 통신 규격 | `1` | API 요청·응답 방식이 호환되지 않게 변경될 때 |
| 게임별 규칙 버전 | 각 게임 `1` | 점수·판정·물리·난수·고정 경기장 조건이 바뀔 때 |

서버는 시작 요청과 제출 요청 모두에서 최소 앱 버전, 통신 규격, 해당 게임 규칙을 확인합니다.
예를 들어 동물 그림만 바뀐 0.3.1은 야구 규칙을 그대로 유지할 수 있습니다.
야구 타격 판정이 바뀐다면 야구 규칙 번호를 올리고 새 시즌을 시작하는 것이 맞습니다.
현재 `ReleaseInfo.Rule`은 세 게임 모두 1을 반환합니다. 일부 게임만 변경할 때는 이 함수를 게임별 분기로 바꿉니다.

앱 버전 문자열만 바꾸면 자동으로 규칙 변경을 감지하는 방식은 아닙니다.
개발자가 변경 범위를 판단하고 앱·서버 정책을 함께 갱신해야 합니다.
클라이언트가 보고하는 버전 값 자체는 위조 방지 수단도 아닙니다.

## 4. 공정한 경기 조건

| 게임 | 온라인 조건 | 순위 기준 |
|---|---|---|
| 야구 | 같은 시즌의 동일 난수 시드, 10구 도전 | 총점 |
| 포트리스 | 동일 시드, 고정 800픽셀 경기장, 10발 도전 | 총점 |
| 러너 | 동일 시드, 고정 480픽셀 코스, 처음부터 560px/s | 생존 시간, 밀리초 단위 |

포트리스와 러너는 모니터 너비에 따라 다른 코스를 주지 않도록 고정했습니다.
그 너비보다 좁은 작업 영역에서는 온라인 시작을 거부합니다.
게임 중 작업 영역이 바뀌어 재배치되면 해당 경기의 온라인 등록을 취소합니다.

러너는 기존 120초 도전을 유지했습니다. 120초 완주자는 공동 순위입니다.
무제한 생존 규칙은 아직 넣지 않았습니다. 추가한다면 새 규칙/시즌으로 분리해야 합니다.
동점은 공동 순위이며, 화면의 동점자 표시 순서는 먼저 달성한 사람이 앞섭니다.
각 사람은 게임·시즌·규칙별 최고 기록 하나만 순위표에 표시됩니다.
낮은 기록으로 최고점이 덮어써지지 않고, 동점 재등록으로 최초 달성 시간이 바뀌지 않습니다.

동일 시드이므로 반복해서 도전하면 패턴을 외울 수 있습니다.
이는 친구끼리 같은 코스 기록을 겨루는 첫 버전의 의도된 방식입니다.
시드도 경기 조건이므로 시즌 도중 몰래 바꾸지 말고 새 시즌과 함께 변경하세요.

## 5. 로컬에서 먼저 실행하기

아래 명령은 저장소 루트의 PowerShell에서 실행합니다.
이 과정은 외부에 서버를 공개하지 않고 현재 PC에서만 연결합니다.

```powershell
Copy-Item .\server\policy.example.json .\server\policy.json

# 실제 사용 시 지인에게만 전달할 무작위 값을 사용합니다.
# 소스 코드나 EXE 안에 넣지 않고 서버 환경 변수로 설정합니다.
$env:TASKBAR_INVITE = [Guid]::NewGuid().ToString('N')

python .\server\server.py --db .\server\data\friends.sqlite --policy .\server\policy.json
```

이미 `policy.json`을 설정했다면 복사 명령을 다시 실행해 덮어쓰지 마세요.
서버가 실행된 상태에서 앱의 서버 주소에 `http://127.0.0.1:8765`를 입력합니다.
초대 코드는 서버 환경 변수에 지정한 값입니다. 별도의 기록을 만들어 지인용 실서버와 섞지 마세요.
로컬 HTTP는 루프백 주소에 한해서만 허용합니다. 다른 PC의 일반 HTTP 주소는 앱이 거부합니다.
검사가 끝나면 서버 터미널에서 Ctrl+C로 종료합니다.

## 6. 실제 지인에게 공개하려면

추가로 결정할 것은 **서버를 운영할 장소**입니다.

1. Python 서버를 계속 실행할 호스트를 준비합니다.
2. SQLite 파일을 재배포·재시작 뒤에도 남는 영구 디스크에 둡니다.
3. HTTPS 역방향 프록시를 구성해 외부 HTTPS 요청을 내부 루프백 서버에 전달합니다.
4. 서버 환경 변수에 초대 코드를 설정합니다.
5. 프로세스 자동 재시작, 디스크 용량 확인, 백업을 설정합니다.
6. 앱 배포 파일을 올린 고정 HTTPS 페이지를 정책의 `download_url`에 넣습니다.
7. 지인에게 앱 ZIP, 서버 HTTPS 주소, 초대 코드를 전달합니다.

내장 HTTP 서버는 로컬 검증/소규모 신뢰 그룹용이며 인터넷에 직접 노출하는 운영 구성을 자동으로 설치하지 않습니다.
처음에는 서버 인스턴스 하나를 사용하세요. 여러 서버가 같은 SQLite 파일을 네트워크 디스크로 공유하는 구성은 이 구현의 대상이 아닙니다.
유료 호스트 가입, 도메인 구매, 방화벽 개방, 실제 서버 배포는 아직 수행하지 않았습니다.
자동 백업 스케줄과 서버 모니터링 역시 호스팅 환경을 정한 뒤 설정해야 합니다.

## 7. 배포 파일 만들기

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test.ps1
python .\server\test_server.py
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\package.ps1
```

결과는 `artifacts/releases/버전-생성시각/` 아래에 생성됩니다.

- `Taskbar_Games.zip`: 실행 파일과 사용자 안내
- `SHA256SUMS.txt`: ZIP의 SHA-256
- `release.json`: 앱 버전·통신 규격·게임별 규칙과 파일 해시

패키지 스크립트는 새 빌드를 만들지만 테스트를 대신하지 않습니다.
ZIP은 생성만 하며 GitHub Releases 등 외부 서비스에 업로드하지 않습니다.
운영자는 ZIP·변경 내역·해시를 고정 배포 장소에 올리고 `download_url`을 설정합니다.
GitHub 비공개 저장소를 배포 장소로 쓰면 지인별 다운로드 권한도 필요합니다.
클라이언트에 저장소 접근용 공용 관리자 토큰을 넣어 배포하지 마세요.

현재 업데이트는 알림과 다운로드 페이지 열기 방식입니다.
자동 다운로드·파일 교체·서명 검증·재시작 기능은 없습니다.
해시는 파일 손상 확인용이며, 신뢰할 수 있는 게시 경로 또는 코드 서명을 대체하지 않습니다.
EXE 코드 서명도 아직 적용하지 않았습니다.

## 8. 업데이트와 시즌 교체 절차

### 디자인·안내 문구만 변경

1. `ReleaseInfo.Version`, 어셈블리 버전, 사용자 안내를 수정합니다.
2. 검사 후 새 패키지를 배포합니다.
3. `policy.json`의 `latest_version`과 `download_url`을 갱신합니다.
4. `minimum_version`, 게임 규칙·시즌·시드는 그대로 유지할 수 있습니다.

### 점수·판정·게임 속도 변경

1. 앱 버전과 해당 게임 규칙 버전을 올립니다.
2. 새 앱을 먼저 배포합니다.
3. 시즌 전환 시 서버의 해당 게임 `rule`, `season`, 필요 시 `seed`를 함께 갱신합니다.
4. 변경된 게임의 구버전 기록은 더 이상 같은 순위표에 제출할 수 없습니다.
5. 저장된 이전 시즌 기록은 삭제하지 않습니다.

### 구버전 전체를 차단해야 하는 버그

`minimum_version`을 수정 버전으로 올립니다. `latest_version`보다 클 수 없습니다.
서버는 시작과 제출 시 현재 정책을 확인하므로, 구버전으로 이미 시작한 경기도 제출이 거절될 수 있습니다.
시즌 도중 긴급 변경이 필요하면 친구들에게 미리 알려 주세요.
정책 파일은 편집한 새 파일을 완성한 뒤 교체하는 방식으로 배포하는 것이 좋습니다.
서버는 매 요청마다 정책을 읽으므로 재시작은 필요하지 않습니다.

정책 예시:

```json
{
  "latest_version": "0.3.1",
  "minimum_version": "0.3.0",
  "protocol": 1,
  "download_url": "https://YOUR-DOWNLOAD-HOST/releases/latest",
  "games": {
    "Baseball": { "rule": 1, "season": "friends-002", "seed": 20261027 },
    "Fortress": { "rule": 1, "season": "friends-002", "seed": 20261028 },
    "Runner": { "rule": 1, "season": "friends-002", "seed": 20261029 }
  }
}
```

`YOUR-DOWNLOAD-HOST`는 설명용이며 실제 주소로 바꿔야 합니다.
첫 시즌은 `friends-001`입니다. 주간 자동 교체 기능은 없으며 운영자가 시즌을 변경합니다.
현재 앱은 현재 시즌만 조회합니다. 지난 시즌은 DB에 보관되지만 조회 UI는 아직 없습니다.

## 9. 기록·계정 보존과 복구

### 플레이어 PC

기존 게임 기록은 `profile.xml`, 온라인 설정은 `online.xml`에 분리되어 있습니다.
둘 다 `%LOCALAPPDATA%\Taskbar_Games`에 있으므로 새 EXE를 다른 폴더에 풀어도 유지됩니다.
게임 기록 형식은 이번 작업에서 변경하지 않았습니다.
계정 토큰은 Windows DPAPI로 암호화해 현재 Windows 사용자에게 묶습니다.
암호화는 개인 PC의 로그인 정보를 보호하기 위한 것이지 치트 방지 기술은 아닙니다.

### 서버 백업

서버 데이터 전체에는 계정·진행 중 경기·시즌별 기록이 들어 있습니다.
운영 중인 SQLite 파일을 단순 복사하는 대신 제공한 온라인 백업 기능을 사용합니다.

```powershell
python .\server\server.py --db .\server\data\friends.sqlite --policy .\server\policy.json --backup .\server\data\backup-2026-10-20.sqlite
```

실제 실행 시에는 날짜를 바꾸세요. 기존 백업 파일이나 원본 DB는 덮어쓰지 않습니다.
초대 코드 환경 변수는 이 명령에서도 설정되어 있어야 합니다.
백업을 같은 디스크에만 두면 디스크 장애 때 함께 잃을 수 있으므로 별도 보관도 필요합니다.
복구할 때는 서버를 중지하고 현재 DB를 별도 보존한 뒤 백업으로 교체하고 다시 실행합니다.
이 복구 절차는 자동 실행하지 않습니다.

### 계정 복구

```powershell
python .\server\server.py --db .\server\data\friends.sqlite --policy .\server\policy.json --recover "지인닉네임"
```

출력된 복구 토큰을 해당 지인에게만 전달합니다.
기존 토큰은 즉시 무효화되고 기록·닉네임·사용자 ID는 유지됩니다.
지인은 앱에서 서버 주소를 입력하고, 초대/복구 칸에 토큰을 넣어 계정 복구를 누릅니다.
여러 PC에서 동시에 같은 계정을 유지하는 기능은 아닙니다.

## 10. 통신 실패와 검증 범위

- 서버가 없어도 기존 오프라인 게임은 실행됩니다.
- 앱 시작 시 업데이트 확인 실패는 팝업 없이 무시합니다.
- 온라인 창에서는 연결 실패를 상태 문구로 표시합니다.
- 네트워크 요청은 작업 스레드에서 처리하고 요청/읽기 제한 시간을 둡니다.
- 로그인 토큰을 다른 호스트에 전달하지 않도록 HTTP 리디렉션을 허용하지 않습니다.
- 시작한 뒤 24시간이 지난 경기, 다른 사용자의 경기, 바뀐 시즌·규칙의 결과는 거부합니다.
- 같은 경기 번호의 같은 결과 재전송은 성공으로 처리하고 중복 집계하지 않습니다.
- 동일 경기 번호에 다른 결과를 넣으면 거부합니다.
- 기본 초대 코드 확인, 토큰 인증, 요청 크기·빈도 제한, 정수·시간 범위 검사를 적용합니다.
- 서버 DB에는 개인 토큰 원문 대신 해시를 저장합니다.
- 입력 재현·서버 물리 시뮬레이션·봇 탐지는 아직 없습니다.

**이 서버는 지인끼리 신뢰를 바탕으로 기록을 겨루는 첫 버전입니다.**
정상 범위 안에서 가짜 점수를 만들어 전송하는 조작까지 완전히 차단하지 못합니다.
상금이 걸린 공개 경쟁이나 불특정 다수 서비스로 바꾼다면 입력 기록 재검증과 운영 체계를 먼저 강화해야 합니다.

## 11. 검증 명령과 수행 범위

기본 `scripts/test.ps1`은 실제 게임 창을 띄우지 않습니다.
게임 규칙·저장·버전 호환·토큰 암호화·완료 경기 수집을 검사합니다.
`server/test_server.py`는 임시 DB와 임시 루프백 서버만 사용합니다.
실제 C# HTTP 클라이언트로 참가 → 정책 확인 → 경기 시작 → 제출 → 중복 재등록 → 내 순위 조회까지 확인합니다.
테스트 자원은 `artifacts/tests` 아래에 만들며 실제 계정이나 사용자 프로필을 수정하지 않습니다.
외부 인터넷 서버 배포, 실제 HTTPS 인증서, 여러 지인의 동시 접속, 화면에서의 수동 조작은 이 검사에 포함되지 않습니다.
